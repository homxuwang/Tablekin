# 发给 WorkBuddy：菜品多图与首图云端迁移

本地前端已按下述协议实现，请完成云端迁移并回传真实角色测试结果。请保留本地已有多图界面与测试，避免用旧单图版本覆盖文件。

## 1. 字段

请先核对 dishes 实际结构、已有数据、表级及列级权限，然后迁移：

- 新增 `image_paths text[] NOT NULL DEFAULT '{}'::text[]`，保存永久存储路径列表，最多9张。
- 保留 `image_path text`，作为首图，必须与 image_paths 第一项一致。
- 无图片：`image_paths=[]`、`image_path=NULL`。
- 回填原来有 image_path 的旧菜品为单元素数组；空字符串首图归一为 NULL。若已有 image_paths，保留合法列表，按现有有效首图排序，不覆盖真实多图。
- 增加数据库约束：一维普通数组（非空时下标从1开始）、最多9项、各元素是非空且非空白路径、无 NULL 元素、无重复路径，image_path 与第一项一致，无图时首图必须 NULL。需要使用校验函数时采用 IMMUTABLE、固定 search_path，明确处理 NULL/空数组，避免 CHECK 的 NULL 值绕过校验。
- 存储路径不写临时文件地址或过期签名 URL。
- 前端同一次 INSERT/UPDATE 提交两个图片字段；云端也必须防止直写造出不一致记录。

请求示例（直接写 dishes，不新增菜品 RPC）：

```json
{
  "name": "番茄炒蛋",
  "image_paths": ["永久路径-b", "永久路径-a", "永久路径-c"],
  "image_path": "永久路径-b"
}
```

首图更换时前端移动顺序并同步 image_path；删除首图时自动选择剩余第一张；删光时提交 [] 与 NULL。

## 2. 权限和存储

- 沿用厨房拥有者及共有人可新增/修改菜品的现有权限；不要放开顾客写入，也不要改变 owner_id 行创建者语义。
- 若 dishes 的 INSERT/UPDATE 使用列级 GRANT，请添加 image_paths 列权限。
- 原有私密厨房/私密菜品 RLS 继续生效；公开查询读取菜品时需返回 image_paths。
- 前端复用已有 `uploadDishImage`、`cloud.storage.sharedPath(user.id, 'dishes/...')`、`createSignedUrls`，不新增 bucket 或猜测平台接口。
- 核查拥有者上传及共有人上传后，合法顾客都能通过签名地址看到公开菜品首图和详情图；不要通过“仅当前上传者可读取”的规则阻断点菜图片，也不要为了测试全面放开私密资源。
- 删除图片只修改菜品引用，不直接删除存储文件，避免未保存编辑破坏现有菜品。孤立上传文件清理暂不纳入本轮。

## 3. 请用真实 authenticated 角色验证

1. 原有单图回填、空图片读取和创建成功。
2. 拥有者、共有人可保存3张图，两个字段一致且重读仍一致。
3. 更换首图后顾客读到正确路径和顺序，签名URL能展示。
4. 删除首图、删除全部图片成功；10张、重复、NULL元素、空白路径、不匹配首图及异常数组被服务端拒绝。
5. 只改菜名或上下架标记不会清空图片。
6. 顾客不能写菜品；非成员读不到私密厨房菜品及图片路径。
7. 共有人上传的图片在该成员退出后，厨房中已有菜品仍能正常展示。
